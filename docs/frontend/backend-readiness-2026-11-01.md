# Проверка backend и перехода на real — 01.11.2026

Проверялись текущие Rust-исходники и локальный процесс на `127.0.0.1:8080`.
Файлы backend, миграции, PostgreSQL, Docker и реализация ИИ не изменялись.
Полная интеграция сейчас **заблокирована**, клиентские сборки не являются
доказательством работоспособности авторизации или реального мультиплеера.

## Живой HTTP/WS

`npm run check:backend` сохраняет очищенный от секретов отчёт в
`apps/client/test-results/backend-smoke.json` и завершает работу с кодом 1
при ошибке либо неполной проверке.

Клиентский `check:release` прошёл: 70 тестов, real/mock build и проверка
изоляции обеих сборок. Это не заменяет отрицательный результат backend smoke.

Проверено на запущенном процессе:

- `/health/ready` и `/api/v2/bootstrap` — 200; bootstrap проходит схему v2.
- `/api/v2/auth/me` без токена и со случайным токеном — 401.
- Вход с заведомо неверным паролем для `player6` — **500 вместо 401**.
  Отдельно `player1` и несуществующий пользователь также получили 500.
- WebSocket с недействительным ticket — 401 до Upgrade.
- Ресурс мира по опубликованному SHA отдаётся без Bearer (HTTP 200).
  Роуты chunks/assets в `http.rs` обходят проверку авторизации и interest.
- Получение `/` строгим Node HTTP-клиентом завершается
  `HPE_UNEXPECTED_CONTENT_LENGTH`. В `http.rs` длина записывается в `write_to`
  и повторно добавляется обработчиком статики. В предложенной TLS-схеме
  статику обслуживает Caddy, но дефект Rust всё равно требует исправления.

PostgreSQL слушает 5432, однако штатный `PgClient::connect` со стандартными
настройками приложения возвращает `role "postgres" does not exist`.
Read-only проверка под текущим пользователем ОС сообщает
`database "discovery" does not exist`. Ничего в кластере не создавалось.
`main.rs` пишет «Connected» без подтверждения соединения, а health не
проверяет готовность базы. Владельцу backend нужны корректные DB_* и миграции.

Успешный login, выдача валидного ticket, авторизованный WS, загрузка interest,
две реальные вкладки и reconnect на этом сервере **не подтверждены**.
Для следующих проверок нужен подготовленный выделенный тестовый аккаунт.
Текущая попытка запуска без пароля явно отражается как blocked, а не PASS.

## Критичные дефекты исходного кода

1. **Пароль не проверяется.** `apps/server/src/auth.rs`, `AuthService::login`
   читает `password_hash`, но не сравнивает с `password`; сразу выдаёт токен.
   Вызов оригинального `auth.rs` в изолированной Rust-обвязке с заглушкой БД
   подтвердил `wrong_password_accepted=true`. Это проверка компонента,
   не успешный вход в текущую живую БД. Исправить до любой публикации:
   реальная проверка password hash, обработка ошибок БД, ограничение попыток.
   Для хранения паролей применять поддерживаемую реализацию Argon2id с солью,
   а не собственное хеширование. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
2. **Токены и tickets не используют криптографический генератор.**
   `generate_id` смешивает время с детерминированным `rand_simple` с фиксированным
   seed. SHA-256 сверху не заменяет CSPRNG. Перевести секреты на OS randomness.
3. **Неполная проверка Origin.** `consume_ws_ticket` проверяет origin лишь
   при его наличии и непустых значениях. Изолированный вызов подтвердил
   принятие ticket без Origin; повторное использование того же ticket отклонено.
   Проверить обязательность/allowlist Origin и членство в сессии до Upgrade.
4. **Неполный WebSocket handshake/frame validation.** `main.rs` выбирает
   subprotocol из ticket, не сверяя предложенный клиентом список и WS-Version.
   `ws.rs::read_frame` допускает немаскированные client frames и не проверяет
   FIN/RSV/корректную последовательность continuation frames. Проверки протокола
   на сервере должны существовать независимо от строгого JS-клиента.
5. **Дата зафиксирована на 31.10.2026.** `ws.rs::rfc3339_now` и
   `competition.rs::rfc3339_at` меняют только часы/минуты/секунды. Это ломает
   время событий, clock offset и deadlines после смены даты/через полночь.
6. **Парсер HTTP читает заголовки одним `read` на 4096 байт.** Разделённые TCP
   пакеты не поддерживаются надёжно; размер тела и заголовки требуют строгих
   лимитов, таймаутов и полноценного разбора. Это видно в `read_http_request`;
   нагрузочное и fuzz-тестирование не проводилось.
7. **Отзыв HTTP-токена не закрывает уже открытый WebSocket.** По исходному коду
   logout только помечает токен, а `run_ws_session` не получает AuthService и
   не проверяет отзыв/expiry во время сессии. Нужна серверная связь lifecycle
   HTTP-авторизации и действующих сокетов; закрытия честным JS-клиентом недостаточно.
   Этот сценарий не воспроизводился на живой БД.
8. **Защита ресурсов мира отсутствует в HTTP-роутах.** До выдачи chunk/asset
   сервер должен проверять пользователя, текущую сессию и разрешённый interest.
   Этот вывод дополнительно подтверждён живым GET без Bearer.
9. **Обход каталога статики.** `http.rs` соединяет `apps/client/dist` с путём
   запроса без canonicalization и ограничения корня. Безопасный raw HTTP-запрос
   `/../../../README.md` вернул 200: файл вне dist действительно доступен.
   Проверялись только публичные данные README, секретные файлы не запрашивались.
   До публикации закрыть traversal, dotfiles и выход через symlinks.

## Блокеры игровых контрактов

Повторно найдены проблемы из [предыдущего аудита](protocol-v2-audit.md):
в `ws.rs` нет lifecycle `quiz.*`; recovery соревнования содержит
`selectedOptionId`, accepted — лишний `optionId`; типы ответов восстанавливаются
как single_choice; GET попыток возвращает `[]` вместо объекта attempts.
Исправлять строгие схемы клиента для принятия этих ответов нельзя.

Конфигурация Rust размещает spawn около `(1,1)`, Софию — `(2,1)`, а читальный
зал опубликован в чанке `c-2-2` около `(80,80)`. Серверу нужны согласованные
world layout, spawn, NPC, коллизии, book/shelf IDs и authority для дверей.
В v2.0.0 нет команды перехода между отдельными кабинетами; frontend не
придумывает её. Изменение wire-контракта требует согласованной спецификации.

Авторизованный HTTP/WS после исправления БД проверять в таком порядке:
неверный/верный пароль → me → create/join → ticket → hello → welcome/interest →
проверка bytes/hash → ready → snapshot → ping → reconnect с новым ticket →
logout и отказ отозванного токена. Полный smoke-проход доступен с переменными
`DISCOVERY_AUDIT_USERNAME`, `DISCOVERY_AUDIT_PASSWORD`, `DISCOVERY_AUDIT_URL`.
Используйте аккаунт, не участвующий в текущей игре: проверка создаёт свою
комнату, затем выходит из неё и отзывает собственный токен.

## Подготовленные изменения клиента

- Явные `build:real`/`build:mock`, отдельные каталоги и `check:release`.
- Нет тихого переключения на mock при ошибке Rust.
- При 401 токен удаляется, ожидающие команды завершаются ошибкой, reconnect
  со старой авторизацией прекращается. Logout очищает клиент даже при сбое API.
- При ошибке восстановления комнаты не создаётся новая комната. Чужая комната
  больше не выбирается по совпавшему отображаемому имени.
- Заблокированное localStorage не ломает вход; испорченный UUID не отправляется.
- API не следует redirect; ресурс проверяется по строгой схеме и текущему миру
  до передачи Bearer. HTTPS → same-origin WSS проверено тестом.
- Неверные учётные данные можно ввести повторно без перезагрузки страницы.

TLS-шаблоны и порядок установки: [tls.md](tls.md).
Локальные кастомные GLB пока находятся вне ResourceLedger; общий лимит 10%
для всех моделей не подтверждён. Потоковый набор по-прежнему учитывается.
Перед production их нужно включить в авторитетный каталог или отдельно
согласовать учёт. Проверка TLS в LAN и производительность на ноутбуках
участников остаются отдельными приёмочными проверками.
