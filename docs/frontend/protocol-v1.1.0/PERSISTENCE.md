# Серверная авторитетность и PostgreSQL 18

Один Rust модульный монолит владеет комнатами и игровым состоянием в памяти. Tokio не должен удерживать глобальные mutex во время SQL, asset IO или AI. Каждая комната/игрок имеет последовательную обработку команд; конкурентные join, ticket consume, cancel/result и config compare-and-swap сериализуются. Никакой клиент не записывает PostgreSQL напрямую.

Рекомендуемые сущности (описание хранения, не обязательные имена таблиц): users и role; access_tokens с hash/expiry/revoked; worlds и content revisions; immutable world_chunks/resources с byteSize/hash; config_revisions с audit и active revision; player_checkpoints user/world/position/progress ref; npc_profiles/knowledge; interactions с уникальным (user,session,requestId) и payload hash; npc_memories с TTL; learning_progress с revision и уникальными knowledge achievement; transactional outbox для config/progress notifications. Tickets могут храниться в RAM при одном процессе; после restart все они недействительны. Нельзя хранить user-password/token в открытом виде.

Активные позиции обновляются в RAM на 20 Hz, не пишутся в БД на каждый input. Checkpoint раз в 5 секунд и на disconnect/leave/shutdown, пакетно. После crash возможна потеря последних ≤5 секунд движения, но не committed прогресса/конфигурации/interaction terminal. Восстановить безопасную проверенную позицию; если старый content revision изменился, использовать spawn и сбросить ссылки на устаревшие чанки.

Транзакция прогресса: взять собственный interaction pending → применить проверенные достижения идемпотентно → увеличить progress revision, если данные меняются → записать memory/result → commit → отправить npc.result и при изменении progress.updated. После потери сокета GET progress и GET interaction восстановят истину. Ни один успех не объявляется до commit. При DB outage не принимать новую награду/изменение config; работа движения может продолжаться до безопасной остановки, health/ready=503. Login при недоступном хранилище возвращает 503.

Config PUT делает проверку revision и запись values/audit/outbox в одной транзакции; проверка отсутствия активных комнат для структурной публикации выполняется под серверной блокировкой публикации. Мир и content revision не меняются посреди комнаты. При restart создаётся новый serverInstanceId, WSS-комнаты не восстанавливаются как непрерывный stream, но durable state сохраняется. Все сокеты проходят новый auth и full sync.

PostgreSQL 18 — фиксированный major; конкретный поддерживаемый patch и image digest выбираются при сборке и фиксируются в офлайн-манифесте инфраструктуры. Данный комплект не поставляет image и не проверяет запущенную БД. Production migrations и rollback/backups — ответственность backend-разработчика, журнал schema migration должен проверяться до /health/ready=200.
